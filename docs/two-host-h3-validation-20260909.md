## H3 direct-path throughput

All rows below used actual CLI TCP forwarding over H3. Both endpoint logs confirmed the native QUIC-IP engine with no WireGuard device and a direct path. Four streams here means four inner TCP streams sharing the H3 tunnel, not four independent QUIC tunnels.

| Run | Server | Duration per iperf measurement | Direction | One stream | Four streams |
| --- | --- | --- | --- | ---: | ---: |
| 1 | A | 10 s | A → B | 41.49 Mbps | 9.11 Mbps |
| 1 | A | 10 s | B → A | 29.95 Mbps | 92.36 Mbps |
| 2 | B | 10 s | A → B | 3.20 Mbps | 33.86 Mbps |
| 2 | B | 10 s | B → A | 43.61 Mbps | 37.88 Mbps |
| 3 | A | 15 s | A → B | 22.43 Mbps | 54.73 Mbps |
| 3 | A | 15 s | B → A | 92.26 Mbps | 77.92 Mbps |

Rates are taken from iperf's **receiver** results. The local sender sometimes accepted substantially more bytes into buffers than reached the remote receiver by the measurement boundary; its higher number is not used as tunnel throughput. Native and tunnel runs were sequential with different warm-up/duration behavior, so this is an indicative comparison, not a tightly controlled congestion-controller A/B experiment.

The variation is material. For example, run 3's complete, SHA-256-checked 12 MiB B → A upload took 20.662 seconds (4.87 Mbps), while a later timed B → A iperf stream reached 92.26 Mbps. Run 2's A → B checked upload took 10.624 seconds (9.47 Mbps). The measurements do **not** support advertising stable high-throughput performance.

## Latency, resources and integrity

Application TCP echo, measured on the remote client itself rather than through the controlling SSH connection:

- Direct-path idle median: 172.63–173.60 ms across the three runs.
- Direct-path loaded medians: approximately 172–176 ms.
- Direct-path loaded p95 reached 615.09 ms in one run; the largest observed echo was 972.73 ms.
- Fresh CLI HTTP data readiness was approximately 2.07–2.75 seconds after the local forward listener was ready.

During run 3, the A/server CLI process used a sampled mean of 32.2% of one CPU core, with a 109.9% short peak and 54.0 MiB peak RSS. The B/client process used 25.4% mean, 85.9% peak and 77.9 MiB peak RSS. Samples covered the entire run, including idle phases. These observations do not exclude a single-goroutine bottleneck or brief scheduling stalls; they do not show sustained whole-process CPU saturation throughout the run.

Runs 2 and 3 each checked 34,079,744 application bytes with SHA-256. Each included a 1 KiB warm-up, a 12 MiB transfer in each direction, four simultaneous 2 MiB transfers split across both directions, and transfers resumed after six seconds idle. Every check passed. No CLI panic was observed.

Run 1's TCP/integrity results also passed, but its overall script result was initially false because its UDP fixture incorrectly assumed numeric CLI `serve` also enabled a UDP listener. That test assumption was corrected rather than labeling it H3 packet loss.

## UDP API versus CLI scope

The current numeric `tailcat serve PORT` implementation registers TCP handlers only. It must not be advertised as implicitly exposing that port over UDP. The library has working `OnUDP` / `DialUDPPort` APIs; the separately compiled `internal/wancheck` driver tests those actual APIs using the same pinned H3 dependencies.

The driver establishes and verifies a TCP echo on the **same Client** before probing UDP, so a successful discovery ping is not mistaken for an authenticated data session. Sequence numbers and full payload bytes are checked; late responses do not count as current-packet success.

| Topology | Payload sizes | Echo requests / valid responses | Observed median RTT |
| --- | --- | ---: | --- |
| B as server, A as client, direct | 64 / 512 / 1200 bytes; 20 each | 60 / 60 | 171.88–172.22 ms |
| A as server, B as client, direct | 64 / 512 / 1200 bytes; 20 each | 60 / 60 | 170.03–170.23 ms |
| A as server, B as client, forced DERP | 64 / 512 / 1200 bytes; 20 each | 60 / 60 | 181.48–188.13 ms |

This is a **180-request echo/integrity sample**, not a sustained high-rate UDP loss test. Do not equate it with the separate native 50 Mbps UDP baseline.

## Test scaffolding and remaining limits

- `scripts/host_pair_probe.py` orchestrates the two-host CLI tests and optional UDP API driver. SSH destinations are supplied only at runtime.
- `scripts/native_pair_probe.py` runs the bounded native TCP/UDP baseline.
- `internal/wancheck/main.go` replaces the previous noncompiling probe that referenced nonexistent `Client.Status` / transport fields. It uses the real UDP APIs and `DiscoPing` for the post-data path check.
- After these scaffolding changes, `go test -count=1 -timeout=180s ./...`, `go vet ./internal/wancheck`, and `git diff --check` passed locally.

Host A's system filesystem was already full before testing. Temporary binaries, fixtures and caches were placed in private `/dev/shm` directories instead. Production disk contents were not cleaned or modified by this task.

**Assessment:** authenticated H3 data transfer, direct and relay reachability, UDP API integrity, concurrency and idle recovery work in this finite test matrix. Throughput and loaded tail latency remain unsatisfactory relative to the available native link. The observations do not isolate BBRv3, H3 DATAGRAM queuing, the userspace TCP stack, or local forwarding as the sole cause. A same-topology, same-duration congestion-controller comparison plus queue/loss/pacing instrumentation is needed before assigning the bottleneck.

This work did not resolve the earlier macOS race-CI `TestUDPForwardIdleTimeout` failure or claim a successful published Release. No DPI-classification, active-probing-resistance, production-uptime or all-NAT-topology certification was performed.
